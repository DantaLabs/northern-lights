## API-key connector attribution

In API-key mode, the connector must send `nl-actor` with an explicit demo service identity. A native MCP connection that supplies only `Authorization` can list tools and read cells, but section preparation is refused as an unattributed operation. Prefer the custom connector header input. If a native connector cannot supply it, configure the demo tunnel to remove incoming `nl-actor` and `X-NL-Actor` headers and supply the fixed service actor `rb03-api-key-demo` before forwarding. Keep bearer-key validation at the server and verify that a bad key still returns 401. This identifies the shared demo API-key session, not a delegated Microsoft user; use Entra for delegated identity. Store tunnel policy, credentials and real endpoints only in ignored local files.

## Refreshing a changed MCP input

After refreshing a tool schema, Copilot can mark its connection Stale. In the test chat, open the connection manager, review the current demo connector, select its existing API-key connection and submit, then retry the original request. Stop for Microsoft sign-in or MFA. Record the connection interruption separately from normal response time; do not send a duplicate prompt while the original request is pending.

The staging-tool code/schema fix in [`internal/mcpserver/tools/section_text.go`](../../internal/mcpserver/tools/section_text.go) exposes `blocks_json`, a JSON-encoded array string for Copilot, alongside the original block array. Exactly one is required. Both paths use the same bounded block schema and existing number, verbatim, actor and preparation guards; this makes Copilot input work without weakening checks. Keep the agent instructions current and refresh the connector after a server update.
