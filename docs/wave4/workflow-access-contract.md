# Wave 4.1 workflow and access contract

Status: Wave 4.1 workflow design frozen for coordinator review. This is a proposed contract; no handler, permission, migration, or provider behavior is implied. The public tool name is `workiva_workflow`; actions are `create`, `get`, `advance`, `pause`, and `cancel`. JSON Schemas in this directory are draft 2020-12 and are closed at every object boundary.

## Authority and identity

The current trusted principal comes from validated Entra claims: tenant `tid`, actor `oid` (with configured subject fallback only where explicitly enabled), token type, authorized client, and permissions derived from configured scopes or the intersection of app roles with client policy. Display labels and payload identity are not authority. **Workflow v1 requires a delegated human principal with validated `tid` and `oid`; application-only identity is not an analyst and cannot impersonate one through payload data.** Existing permissions include `workiva.read`, `workiva.write.preview`, `workiva.write.confirm`, `workiva.visual_ack`, `reconciliation.manage`, `tenant.admin`, and assurance capabilities. **There are no workflow-specific capabilities in the current permission vocabulary.** The capability names below are proposed additions and must be configured in the Entra policy and enforced by handlers and transport before enablement:

| Proposed capability | Applies to |
|---|---|
| `workflow.create` | Create a run, after all referenced artifacts and profiles pass their own access checks |
| `workflow.read` | Get a run and its steps, after tenant and actor isolation checks |
| `workflow.advance` | Derive and persist the next eligible step/preview request |
| `workflow.pause` | Pause a run and prevent future step admission |
| `workflow.cancel` | Cancel future work and prevent future step admission |

Workflow ownership is the tuple `(delegated trusted tenant_id, delegated trusted actor_id)`. Every lookup, idempotency reservation, event, and child-step association is scoped by that tuple. Payload fields never include tenant or actor. A caller with a different actor in the same tenant receives the same non-disclosing `not_found` response as for an absent run; cross-tenant IDs receive no data. Creation checks each referenced source/draft artifact against the same trusted tuple and rechecks it on use. A workflow grants no authority over its referenced artifacts, destination profile, Workiva resource, transfer, or operation.

The existing transfer path requires a trusted principal and `workiva.write.preview` to stage; confirm separately requires trusted identity and `workiva.write.confirm`; visual acknowledgement and reconciliation have their own existing permissions. Workflow `advance` cannot call a content placement confirmation, transfer confirmation, provider write, or visual acknowledgement. Each mutation is executed through the existing or future reviewed content/transfer surface, under that surface's own authorization, exact preview and single-use confirmation. The workflow step plan is immutable after create; execution evidence is append-only runtime state. A separate content/transfer operation appends its server-produced association `(workflow_id, step_id, placement_intent_id or transfer_id/operation_id)` after the normal tool result exists. A verify step binds to that persisted association and a machine read-back result. The correlation design below is frozen as a proposed contract; handler/schema implementation and acceptance remain gates. No association ID or completion claim is accepted from `advance` input.

Every materializing action (`create`, `advance`, `pause`, `cancel`) requires a trusted actor, its proposed action capability, an ingress idempotency key, canonical request digesting by the server, audit availability, and an atomic durable state-plus-audit/idempotency outcome. Get requires `workflow.read` and emits a read audit event; it does not reserve a write idempotency key. Authorization precedes scoped idempotency lookup. Reusing a key with a different canonical request returns `idempotency_conflict`; an in-flight identical request returns `idempotency_in_progress`; a completed identical request replays its immutable response without provider work or token reconstruction. Raw idempotency keys and confirmation tokens are never stored or logged. If required audit/state sealing fails, the action fails closed and reports an unknown/reconciliation disposition where commit outcome is uncertain.

## Bounded linear run and server-owned state

A run contains 1–16 immutable steps in declared order. Step IDs are unique bounded opaque identifiers. Every step has an explicit `depends_on` array containing only unique IDs of earlier steps; the first step has an empty array. This gives a bounded acyclic linear order while allowing a step to wait on multiple earlier prerequisites. No loops, branching expressions, arbitrary code, user-authored tool names, or autonomous scheduler instructions are accepted. The step kinds are `read`, `draft`, `mutation`, and `verify`; each kind has only the closed reference fields shown in `workflow.input.json`. A read selects an exact mapped field name for the existing `workiva_get_field` or a signed approved report/field revision for `workiva_snapshot_report`. Direct source-artifact reads are not accepted as workflow read steps and have no public get surface; they remain a requested internal owned-artifact resolver seam. Source artifacts may still be immutable inputs to draft or placement steps. A route mutation selects a signed `route_id`/revision/hash; the server resolves that active route and maps it to the existing transfer tool's source/target/conversion selectors. It does not add a route parameter to or change the meaning of `workiva_transfer_value`. A placement mutation selects a source or draft artifact and signed DestinationProfile. Client IDs, revisions, and hashes are optimistic selectors only: the server resolves trusted records and compares exact revision/hash before accepting them. They are not model authority. Server-assigned step and run states are not input fields.

`advance` takes only a run ID and action idempotency key. The service computes readiness from persisted dependency states, immutable artifact/profile/route bindings, and linked operation/verification records. It never accepts a caller assertion such as `completed`, `verified`, `operation_id`, or `step_status`. A step becomes complete only from a persisted server-side result appropriate to its kind. A mutation step is complete only when its own associated mutation has a terminal machine outcome; a `verify` dependent on that mutation completes only when an uncached read-back result for the same intent and operation is persisted. Human visual acknowledgement is separate and cannot substitute for machine verification. `advance` returns a closed `next_action` pair (`tool`, `kind`) selected from the output schema; it cannot execute a request or accept a tool name. `workiva_get_field`, `workiva_snapshot_report` (`snapshot_read`), and `workiva_transfer_value` are existing surfaces. The content-placement `ingest_draft`/`stage_placement` pair is proposed integration behavior, not a current callback or executable tool capability. When no step is eligible, it returns the appropriate `waiting`, `blocked`, `completed`, or `paused` outcome derived from stored state. Unknown side effect returns a reconciliation envelope carrying the actor-owned workflow and a typed reconciliation error, not a generic denied/error envelope that discards useful private state.

Any failed, expired, denied, stale, unknown, or reconciliation-required prerequisite blocks dependent steps. Unknown mutation outcome freezes that mutation and requires the existing reconciliation path; no retry or subsequent dependent submission is automatic. Each mutation requires its own preview and separately confirmed execution. Confirmation binds the exact source/draft artifact revision and content hash, destination profile or transfer-route revision/hash, target, intended content, policy/version bindings, actor, expiry, and intent. Editing any bound item requires a new intent and confirmation. Cancel stops admission of future steps; it cannot undo completed writes. Pause blocks all future advance; there is no resume action in this five-action schema, so paused runs remain paused pending a separately designed, authorized resume contract. A cancelled run cannot resume.

## External result correlation contract

When `advance` returns a `next_action` that calls a separate operation, it also issues a bounded `workflow_context` object with exactly `{workflow_id, step_id, binding_id}`. The output's separate `binding` object exposes `step_kind`, `prerequisite_hash`, and `expires_at`. `binding_id` is opaque and unpredictable; server storage binds it to the trusted tenant and delegated actor, run ID, step ID/kind, canonical hash of immutable prerequisite results and selected references, issue time, and expiry. Expiry is no later than the minimum configured run TTL, step TTL, and signed `workflow_ttl.binding_limit_seconds` (operator-selected 1–900 seconds). A binding is single-use except for idempotent replay of the same canonical downstream request. It is correlation only: it is never an actor identity, permission, destination authorization, confirmation, or source of completion truth.

The content tool's optional closed `workflow_context` on `ingest` and `stage` has exactly those three fields. Before materializing an artifact, preview, or reading a Workiva target, the service validates the binding against the current authenticated delegated tenant/actor and persisted run, step, kind, prerequisites, state, expiry, and expected action. A draft step derives its source from `verified_evidence_refs` that resolve to already persisted, owned, completed workflow evidence; it does not accept repeated source bytes or caller-selected evidence authority. It binds the generated draft's server-returned `id`, `revision`, and `sha256` plus its source evidence to the step. A stage operation binds its new `placement_intent_id` and preview hash to the mutation step. Domain association, audit event, and idempotency envelope append atomically. A token-free replay returns the identical association; a binding presented for another actor, run, step, action, or different request conflicts and performs no materialization/provider work.

The existing `workiva_transfer_value` and read tools keep their current operation meanings. Their optional workflow correlation is a separately versioned, additive and gated schema extension targeted for Wave 4.3; it has the exact same three-field `workflow_context` and the same binding validation/association rules. A resolved signed route is mapped to today's transfer selectors; no new public route execution semantics are implied. Until those future correlation fields and atomic association paths are implemented and accepted, the example is a proposed sequence, not an executable production workflow. A pre-existing draft may be selected at create with its immutable ID/revision/hash, but cannot stand in for a summary generated from a future verification result.

Workflow and step states are server vocabulary: run `active`, `paused`, `cancelled`, `completed`, `blocked`, `reconciliation_required`; step `pending`, `ready`, `in_progress`, `completed`, `failed`, `blocked`, `unknown`, `cancelled`. The result and audit record preserve state transitions. There is no all-plan approval and no cross-file atomicity or automatic rollback.

## Artifact, draft, profile, and version bindings

The content peer owns the source/draft/placement contract. Workflow source references use `source_artifact_id` and `content_hash`; extracted-item references use `source_artifact_id`, `extracted_item_id`, `revision`, and `content_hash`; draft references use `draft_artifact_id`, `revision`, and `content_hash`. The content response field `source.sha256` is the raw source-byte hash and has the same source-artifact semantics as workflow `content_hash`; derived content hashes bind their exact extracted item or draft revision. Source artifacts are immutable and have no mutable revision counter. Destination profiles and signed transfer routes bind by ID, positive revision, and canonical content hash. Caller-supplied IDs/revisions/hashes are optimistic selectors only: the service resolves the trusted object and compares server-stored values before accepting them. These values never authorize the caller. Draft steps bind source step IDs at plan creation; their output draft association is appended only after eligible content ingest. Draft records retain exact persisted source evidence references and hashes. A verify step binds its mutation step ID, placement intent ID or transfer/operation ID, and persisted machine verification result.

`DestinationProfile` is a **proposed signed bundle extension**, not a current bundle kind. Add an operator-authored profile ID, positive revision, tenant binding via the containing bundle, immutable content hash, active/retired state, permitted target Workiva resource/sheet/single-cell locator or approved selector, allowed operation/content kind and conversion policy revision, format/formula/protection constraints, resource-policy reference, provider-metadata requirements with explicit `verified`, `operator_declared`, or `unavailable` provenance, and retention class. Reject secrets, credentials, executable content, unknown fields, unbounded strings/collections, unresolved references, reused revision with changed content, and profiles that imply formula/layout/multi-cell/bulk writes. Bundle signature authenticates canonical operator bytes; semantic validation and runtime authorization remain required. Profile removal from a new complete active bundle disables it for new previews but retains historical binding data needed to explain existing intents. Existing code has signed bundles, revision/hash checks, exact routes and conversion policies, and actor/resource read allowlists; none of those currently proves a DestinationProfile, target metadata, write permission, or delegated Workiva user identity.

For step associations, a `draft` step consumes either one immutable `source_artifact` reference or IDs of earlier persisted evidence-producing steps in both `source_step_ids` and `depends_on`; verification evidence is allowed as source for a downstream summary. Its draft artifact is output data, not supplied at create unless it already exists as an independently created immutable candidate. A mutation consumes exactly one source artifact, draft artifact, or earlier draft step (`draft_step_id`) plus one profile reference; a step-produced draft must be a declared dependency. A verify step names exactly one earlier mutation step in `mutation_step_id`, and that ID must also be a dependency. At runtime, the server appends the mutation step's placement intent and transfer/operation association, then binds verification to that same association and a persisted uncached read-back. These relational rules are semantic validation at create/advance in addition to JSON Schema; client-supplied output IDs, completion or operation associations are rejected.

## Provider access mode and analyst isolation

The plan records one configured Workiva API grant today and explicitly says Entra identity does not map automatically to Workiva user permissions. Therefore neither app authentication nor an existing resource relationship allowlist proves that Workiva honors the individual analyst's access.

For the interim shared-grant model, extend the **proposed signed operator bundle** with a closed `workiva_access` object selecting `mode: "shared_grant_restricted"`, a named provider grant reference (identifier only, never credential material), and an explicit non-empty allowlist of canonical Entra `(tenant_id, actor_id)` pairs authorized to use that grant. Bind each allowed actor to the permitted DestinationProfile IDs/revisions and resource IDs, allowed workflow/content capabilities, and effective interval. Reject an absent/empty actor allowlist, unknown mode, wildcard actor/resource, mismatched tenant, expired grant/profile, or unresolved profile. Before enablement, code must enforce this allowlist at create, get, every advance, preview, and immediately before mutation; apply the allowlisted actor/resource/profile restriction even though Workiva itself sees the shared grant. This is a **proposed restriction**, not runtime behavior today. Do not claim that the current service enforces a single analyst. The initial release remains single-analyst operationally until this signed selection is implemented and its configured actor is verified; a second analyst is prohibited until actor isolation is accepted. Shared-grant resource restrictions are Northern Lights controls and do not become native per-user Workiva authorization.

Future `user_delegated` access is a separate mode requiring verified per-user credential delegation, token audience/scope, provider-side access checks, expiry/revocation behavior, and audit evidence. It must not be inferred from Entra login and must not silently fall back to the shared grant. Mode changes require a newly signed bundle and explicit operator acceptance.

## Retention, deletion, audit, and restore

Freeze these fail-closed rules now; operators must supply actual durations and legal-hold values before release. Each source artifact, draft artifact, workflow run/step, placement intent, and evidence record is assigned a signed operator retention class and immutable policy revision at creation. Missing, inactive, invalid, or unresolved class/policy blocks creation and any transition that would extend retention. No guessed default duration. A run or artifact expiry never shortens a longer bound child record or a legal hold. Deletion is denied during legal hold, unresolved operation/reconciliation, active workflow step, or incomplete audit/backup disposition. Expiry creates a durable tombstone before deleting external bytes; failure or unknown delete disposition remains `reconciliation_required`, and metadata is retained to reconcile. Purging user content never deletes audit chain entries, confirmation digests, mutation/verification association, or the minimal tombstone needed for replay and recovery. Workflow cancellation is not deletion.

Audit events must identify trusted tenant/actor, run and step IDs, action, prior/new state, idempotency record, artifact/profile revision hashes, linked intent/operation/verification IDs, and policy revision. Avoid source bodies, extracted text, generated draft bodies, raw credentials/tokens, and sensitive provider payloads in ordinary audit rows. Preserve enough immutable references and hashes to replay decisions without retaining user content past its authorized lifetime. Audit-chain integrity does not by itself establish audit completeness.

Workflow, step, artifact, and association persistence must be included in the same tenant backup/restore and signed manifest accounting as existing records, with schema markers and counts. A restore must validate tenant, hashes, audit links, artifact availability, and operation/fence joins before admitting writes. Startup may validate and recover records, expire stale reservations, and quarantine uncertain mutations; **startup never resumes a workflow, advances a step, polls/submits a provider operation, or repeats a write**. Restored runs with missing artifacts/profiles, mismatched hashes, unavailable provider facts, incomplete backup, or unknown mutation outcomes remain blocked/reconciliation-required. Backup RPO/RTO are operator targets, not guarantees; existing Azure Blob fence admission remains a separate prerequisite.

## Error vocabulary and disposition

The output schema fixes these codes: `invalid_request`, `missing_field`, `unknown_field`, `invalid_value`, `bounds_exceeded`, `strong_identity_required`, `permission_denied`, `not_found`, `artifact_not_found`, `artifact_access_denied`, `artifact_revision_mismatch`, `profile_not_found`, `profile_inactive`, `profile_access_denied`, `access_mode_unconfigured`, `actor_not_allowlisted`, `provider_access_unverified`, `retention_policy_missing`, `legal_hold`, `workflow_state_conflict`, `step_not_eligible`, `prerequisite_incomplete`, `mutation_association_missing`, `verification_mismatch`, `stale_binding`, `confirmation_required`, `feature_disabled`, `idempotency_conflict`, `idempotency_in_progress`, `audit_unavailable`, `persistence_unavailable`, `reconciliation_required`, `internal_error`. Ordinary denials/errors/unavailable results have at least one error and no private workflow/step payload. `status: reconciliation_required` is the explicit exception: it includes only the authenticated owner's run, a required `reconciliation_required` error and `reconciliation_required: true`, with retryable false. `replayed` is separate metadata; it never replaces the original business status. `get` is not idempotency replayed. Every tool result requires `nl_audit_id`; a request rejected by authentication middleware before tool dispatch has no tool result and is the explicit safely non-audited transport failure. Errors disclose no existence across actor/tenant boundaries. `retryable` is true only for a proven pre-effect transient; unknown side effect is never retryable. Responses always state `no_mutation_submitted: true`; workflow actions never submit a Workiva mutation.

## Operator policy shape and hard ceilings

`schemas/workflow.operator-policy.json` is the exact proposed closed payload for the signed operator-selected access and retention extension. It permits only `shared_grant_restricted`, exactly one analyst entry, a credential-free opaque provider grant reference, bounded approved profile/resource/capability lists, and finite effective dates. It separately requires operator-supplied run, step, idempotency replay TTLs and source/draft/workflow/audit retention durations/legal-hold values. The numeric bounds in the schema are ceilings, not chosen values or a recommendation. The UUIDs in examples are synthetic fixtures and must never be copied into an operator bundle. The signed schema extension is not in the current bundle validator and has no current runtime enforcement.

The maximum serialized request body is 65,536 UTF-8 bytes (enforced before JSON decode; not representable by JSON Schema). Hard ceilings are 128 ASCII characters per workflow idempotency key, 16 steps/run, run TTL 604,800 seconds, step TTL 86,400 seconds, idempotency replay TTL 604,800 seconds, and each content retention duration 315,360,000 seconds (ten-year schema ceiling). Actual TTL and retention values must be explicitly supplied in signed operator policy and validated at runtime; missing values block create/advance/purge as applicable. These ceilings do not assert retention law or operator policy.

## Operator values and implementation/release gates

1. Operator: which Entra tenant/object ID is the sole initial analyst, and who approves the explicit signed allowlist? Until set and enforced, `access_mode_unconfigured` / `actor_not_allowlisted` blocks enablement.
2. Operator: which named shared Workiva grant, approved profile/resource IDs, scopes, effective interval, and revocation process are allowed? Credentials never enter the bundle. Missing values block writes.
3. Operator: which source/draft/workflow/audit retention classes, durations, legal holds, and deletion authority apply? Missing policy blocks create/advance and purge.
4. Implementation gate: add the defined workflow_context/binding validation and atomic association to content ingest/stage; add the same shape as a separately versioned additive extension to transfer/read tools in Wave 4.3. Until those handlers/schema extensions pass actor-isolation, expiry, replay, prerequisite and atomicity acceptance, dependent steps remain feature-disabled. This is an implementation/release gate, not an unresolved design decision. Content schema review must expose the signed DestinationProfile's immutable content hash alongside ID/revision before that selector can be enabled.
5. Operator/provider spike: identify required destination metadata and its provenance, formula/protection checks, and which facts are provider-verified versus operator-declared. Unknown critical facts block affected writes.
6. Operator/release: decide whether shared-grant restrictions are acceptable after independent actor-isolation evidence. Until then, the release remains single-analyst operationally and multi-analyst use is disabled.
7. Identity handoff: prove the actual Copilot/flow-to-service path preserves a delegated human Entra `tid`/`oid` (including any OBO/delegation behavior). App-only flow identity cannot authorize on behalf of a payload-supplied actor. Until a delegated human principal is verified at intake, workflow create and all artifact correlation are disabled. Do not assume application-role policy grants human authority.
8. Operator: provide signed maximum run lifetime, step lifetime, idempotency replay window, and source/draft/workflow/audit retention/legal-hold values before enablement. These are required but unset; hard ceilings are specified above. Missing/over-limit values block relevant operations. No real identity or retention choice is included in this design.
9. Current pause has no resume action. A paused run is safely frozen; adding resume requires a separately reviewed capability, audit event, and transition rule.
